# DEP-01 云服务器部署决策基线

**状态：** 基线已冻结，采购方案已选定，实际资产值待购买后登记

**适用版本：** `develop@7726b06`及后续部署分支

**决策输入：** 项目负责人确认使用已购买的云服务器部署

**冻结Spec：** V1.3

## 1. 目的与边界

本文冻结第一版生产部署的架构、安全边界和运维责任接口，作为后续
`DEP-02`至`DEP-10`的唯一部署输入。

本文不记录真实密码、私钥、完整证书、数据库、学生数据或原始Excel。
公网IP、域名和厂商账号只登记在授权的运维资产台账中；仓库只保留变量名和非敏感决策。

原`docs/spec.md`冻结方向为“校园内网单机部署”。本次负责人已指定改为购买的云服务器，
因此后续正式发布前必须更新Spec部署章节的版本说明；本任务不直接修改冻结Spec。

## 2. 冻结架构

第一版采用单机、单Django实例、SQLite持久化架构：

```text
公网用户
  -> 云厂商安全组（仅开放80/443；SSH限制来源）
  -> Nginx容器（HTTPS终止、静态文件、请求限制）
  -> Django + Gunicorn容器（单实例）
  -> SQLite、媒体和备份持久化目录
```

冻结决定：

1. 使用Docker Engine和Docker Compose插件部署，不安装Kubernetes。
2. Nginx为第一版必选组件，不直接向公网暴露Django端口。
3. 公网服务必须使用HTTPS；80端口仅用于证书签发和跳转到443。
4. Django业务容器只运行一个实例，避免SQLite多实例写入竞争。
5. 第一版继续使用SQLite，不在部署阶段临时迁移到其他数据库。
6. Gunicorn使用单worker起步；线程数和超时由部署验收确定。
7. Bootstrap等浏览器运行时资源必须本地化，不依赖公网CDN。
8. 所有正式数据必须位于宿主机持久化目录，不进入镜像可写层。
9. 数据恢复必须在停止Web写入后执行，不提供在线替换SQLite的Web接口。
10. 正式部署只允许使用已评审的Git tag或固定提交，不部署浮动工作分支。

## 3. 宿主机基线

推荐并冻结以下最低基线；实际已购服务器不得低于该基线：

| 项目 | 决策 |
| --- | --- |
| 操作系统 | Ubuntu Server 24.04 LTS 64位；若已购实例不是该系统，部署前重装或形成兼容性例外记录 |
| CPU | 最低2 vCPU |
| 内存 | 最低4 GiB；低于4 GiB不得直接生产上线 |
| 系统盘 | 最低40 GiB SSD |
| 数据空间 | 上线前至少保留20 GiB可用空间，并按Excel、数据库和备份增长复核 |
| 时间 | 时区`Asia/Shanghai`，启用系统时间同步 |
| 容器 | Docker Engine稳定版与Docker Compose v2插件 |
| 管理账号 | 禁止日常直接使用root；使用具备sudo权限的专用运维账号 |
| SSH | 仅密钥登录，关闭密码登录和root远程登录 |

若实际云服务器不满足任一项，DEP-03开始前必须记录偏差、影响和负责人批准。

## 4. 网络、域名与TLS

| 项目 | 决策 |
| --- | --- |
| 公网入口 | 仅Nginx对外提供服务 |
| 对公网开放 | TCP 80、443 |
| SSH端口 | 安全组仅允许负责人固定IP或可信VPN来源访问，不向全网开放 |
| Django端口 | 仅Compose内部网络可达，不映射到公网 |
| 域名 | 正式上线必须使用备案/合规且由项目方控制的域名或子域名 |
| TLS | 使用受信任证书；自动续期并设置到期监控 |
| HTTP | 所有业务请求跳转到HTTPS |
| 代理信任 | Django只信任Nginx容器的转发协议，不信任任意客户端伪造的转发头 |

在域名和证书未就绪前，只允许通过受限IP进行部署演练，不得导入真实学生数据。

## 5. 数据与目录

宿主机推荐根目录为`/srv/party-archive`，冻结逻辑布局如下：

```text
/srv/party-archive/
  app/                 # compose文件和版本化部署配置
  data/database/       # db.sqlite3及SQLite边车文件
  data/media/          # 原始Excel、导入快照和媒体文件
  data/static/         # collectstatic输出
  data/backups/        # 本机一致性备份
  data/logs/           # 仅在确有文件日志需求时使用
  secrets/             # .env和证书引用；不进入Git
```

规则：

1. 数据目录使用宿主机绑定挂载，便于备份、审计和迁机。
2. 数据库、媒体和备份分别挂载，避免容器重建造成数据丢失。
3. `.env`权限限制为仅运维账号可读，不提交Git。
4. 镜像、Compose配置和数据目录分离。
5. 本机备份不等于完整备份，必须另存到第二故障域。
6. 正式数据不得写入仓库目录、镜像层或临时目录。

## 6. 备份与恢复决策

| 项目 | 决策 |
| --- | --- |
| 导入前 | 创建SQLite一致性备份，并保存当前媒体索引 |
| 导入后 | 再创建一次一致性备份 |
| 周期备份 | 至少每日一次；原Spec的每周频率作为最低下限，不适用于公网云服务器唯一副本 |
| 本机保留 | 最近7个每日备份及最近5个导入前后备份 |
| 异机备份 | 至少每日复制到云厂商对象存储或另一台授权设备 |
| 加密 | 异机备份必须加密传输并限制读取权限 |
| 校验 | 保存SHA-256并执行SQLite完整性校验 |
| 恢复演练 | 正式上线前至少完成一次异机恢复；上线后至少每季度一次 |

恢复目标：

- RPO（可接受数据丢失窗口）：不超过24小时；每次正式Excel导入前后均额外备份。
- RTO（目标恢复时间）：4小时内恢复到最近一次已验证备份。

对象存储桶名称、区域、访问凭据和生命周期策略必须登记在授权运维台账，不写入仓库。

## 7. 安全与隐私边界

1. 公网部署涉及学生个人信息，正式导入前必须确认组织授权、隐私告知、访问范围和数据保存期限。
2. 默认拒绝搜索引擎索引，禁止将管理页面公开宣传。
3. 管理员账号必须使用强密码；首个管理员由运维人员在服务器上交互创建。
4. 生产环境必须`DEBUG=False`，缺失密钥或域名配置时拒绝启动。
5. Session和CSRF Cookie必须仅通过HTTPS传输。
6. Nginx限制请求体大小，并对登录与上传入口设置合理速率限制。
7. 安全组、宿主机防火墙和应用权限采用最小开放原则。
8. 日志不得记录密码、Session、完整学生资料或原始Excel内容。
9. 操作日志中的来源IP只接受经过明确配置的Nginx可信代理链。
10. 上线前完成依赖漏洞检查、Django部署检查和基础安全扫描。

| 角色 | 责任 | 当前登记 |

| 数据负责人 | 批准真实Excel导入和数据校验 | 待登记 |
| 安全/隐私负责人 | 审核公网暴露和学生数据合规性 | 待登记 |

发布规则：

1. `develop`不直接部署生产。
2. 生产部署使用带版本号的Git tag和不可变镜像标签。
3. `latest`只能作为便捷别名，不能作为回退依据。
4. 每次发布前保存数据库、媒体索引、环境变量键名清单和当前镜像摘要。
5. 至少保留当前版本和上一个已验证版本，支持应用回退。
