## 2. 当前事实与问题

截至2026-08-31，学生认证、学生档案、管理员查询、Excel解析、上传预览、正式导入、
最近成功批次回滚、SQLite灾难恢复及合成验收工具均已进入`develop`。DEP-01至DEP-07的
通用代码和文档也已进入`develop`，其中包括生产配置、Docker镜像、Compose、Nginx、
本地静态资源、健康监控和COS备份自动化。

当前仍不能形成发布结论，原因如下：

1. `docs/current_project_status.md`的事实基线停留在2026-08-22，落后于部署合并结果；
2. 尚未冻结新的发布候选SHA；
3. 当前SHA尚无一次完整、未超时的全量测试结果；
4. 约1500条合成数据验收尚无与当前SHA绑定的正式报告；
5. Docker构建和容器冒烟尚未进入CI；
6. 尚无正式Release Tag、不可变镜像摘要或生产部署证据；
7. 云资产、域名证书、异机备份目标和运维责任人仍未登记。

## 3. 收敛原则

1. 只对一个固定SHA作出发布判断，不继承旧SHA的测试结论。
2. 任何代码、依赖、迁移或生产配置变更都会使既有候选失效并重新执行门禁。
3. 合成验收不得写入正式数据库、正式媒体目录或真实学生数据。
4. 本地通过不代替GitHub Repository policy、Ubuntu和Windows CI通过。
5. 部署配置契约通过不等于镜像已构建、容器已启动或服务器已上线。
6. 阻断项必须记录负责人、证据位置和处理结论，不以口头确认代替。
7. `develop`不直接用于生产；基线通过后再创建发布PR和版本Tag。

## 4. 工作包

### BASE-01：事实与仓库状态校准

**目标：** 建立唯一可信的当前状态入口。

**任务：**

- 将`docs/current_project_status.md`更新到当前`develop`基线；
- 核对DEP-01至DEP-07的提交和文件是否进入`develop`；
- 区分功能合入、专项验证、CI验证和生产验证四类状态；
- 记录`main`与`develop`差距、现有Tag和未完成发布任务；
- 将过期Sprint文档继续保留为历史资料，不反向覆盖当前状态页。

**完成条件：** 状态页、Git提交历史和实际文件一致，且不再出现“Docker未开始”等过期结论。

### BASE-02：冻结发布候选

**目标：** 确定后续全部验证使用的唯一SHA。

**任务：**

- 收集当前仍准备合入`develop`的必要修复；
- 除阻断性修复外停止向候选混入新功能；
- 候选分支必须基于最新`origin/develop`且工作树干净；
- 记录候选SHA、依赖锁定文件哈希和数据库迁移集合；
- 暂定候选命名为`v1.0.0-rc.1`，通过门禁前不得创建正式Tag。

**完成条件：** 团队确认一个固定候选SHA，后续报告均包含相同`git_sha`。

### BASE-03：代码与数据库回归

**目标：** 证明候选业务代码和数据库结构完整。

**必跑命令：**

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --noinput
python manage.py test -v 2
python scripts/ci_guard.py --post-test
git diff --check
```

同时复核Repository policy、Ubuntu和Windows三类GitHub Actions结果。若本地全量测试超时，
必须调整执行环境或按测试模块分片并保留所有分片结果；不得把“超时前未见失败”记为通过。

**完成条件：** 本地全量或完整分片、Ubuntu CI、Windows CI全部通过，无遗漏迁移和测试污染。

### BASE-04：约1500条联合验收

**目标：** 在同一候选SHA验证Excel完整业务链路。

**任务：**

- 使用固定种子`20260822`和约1500名合成学生运行验收执行器；
- 验证九支部、负向上传、两次确认导入、管理员与学生查询、最近批次回滚及重启复查；
- 核对原始Excel、preview、rollback和SQLite备份证据的SHA-256；
- 确认`acceptance_report.json`中的`git_sha`等于候选SHA且`restart_verified=true`；
- 验收产物保存到被Git忽略的授权目录，不提交Excel、SQLite或媒体文件。

**完成条件：** 报告全部门禁满足，统计与数据库抽样一致，没有真实个人信息。

### BASE-05：部署基线专项验证

**目标：** 确认DEP-01至DEP-07没有因集成产生回归。

**任务：**

- 运行生产设置、Dockerfile、entrypoint、Compose、静态资源、健康检查和备份自动化专项测试；
- 使用示例变量执行`docker compose config`；
- 执行`manage.py check --deploy`并人工审查必要例外；
- 复核Web容器单实例、非Root运行、数据库/媒体/静态/备份绑定挂载；
- 确认Nginx是唯一公网入口，Django端口没有宿主机端口映射；
- 记录DEP-08仍需完成的真实镜像构建和容器冒烟范围。

**完成条件：** 专项测试及静态配置检查通过，未完成的动态验证进入DEP-08，不被误记为已验证。

### BASE-06：证据与缺陷收敛

**目标：** 让发布结论可追溯。

**证据清单：**

- 候选SHA和分支；
- 完整测试命令、时间、平台、Python与依赖版本；
- CI运行链接和结论；
- Excel验收报告路径及SHA-256；
- Compose解析和部署专项测试结果；
- 未解决缺陷、风险等级、负责人和计划版本；
- 数据库迁移清单；
- 仓库敏感文件扫描结论。

严重度为P0或P1的缺陷必须修复后重新冻结候选。P2缺陷只有在不影响数据正确性、安全、
权限、备份恢复和核心可用性时才允许由负责人书面接受。

**完成条件：** 证据索引完整，不依赖个人电脑上的临时口头结果。

### BASE-07：发布评审与后续移交

**目标：** 对候选作出明确的Go、Conditional Go或No-Go决定。

**Go条件：**

- BASE-01至BASE-06全部完成；
- 不存在未接受的P0/P1缺陷；
- 同一候选SHA的本地、双平台CI和1500条验收全部通过；
- 仓库不含真实数据、密钥、数据库或备份；
- DEP-08至DEP-10的责任人、顺序和输入已经登记。

基线Go只表示允许进入发布工程，不表示允许导入真实数据或开放公网。之后依次执行：

```text
DEP-08 容器构建与冒烟CI
→ DEP-09 部署、升级、回退和故障手册
→ DEP-10 脱敏发布候选与异机恢复演练
→ develop到main发布PR
→ RC Tag
→ 正式发布审批
```
