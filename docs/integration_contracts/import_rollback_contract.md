## 3. 回滚证据

正式导入前必须在批次服务端目录原子生成：

```text
rollback_snapshot.json
rollback_snapshot.sha256
pre_import.sqlite3
```

JSON快照至少包含`schema_version`、`import_batch_id`、`created_at`、`record_count`和`students`。每个学生记录必须标识`student_existed_before`，并保存导入前Student、ApplicationRecord、IdeologicalReportSummary和有效IdeologicalReport的可恢复字段。

日期采用ISO格式，外键保存稳定主键，不保存密码、Session、文件内容或可执行对象。快照只能由服务端根据数据库当前状态生成，不能接收客户端重建结果。快照写入后计算SHA-256；任一保护文件生成失败时不得开始正式业务写入。

## 4. 可回滚判定

批次必须同时满足：

1. 状态为`success`且尚未回滚；
2. 是当前最新成功批次，不存在后续成功批次；
3. JSON快照存在且哈希、schema、batch ID和记录数有效；
4. 当前受影响数据仍能安全归属于该批次；
5. 未检测到无法解释的后续业务修改。

任一条件不满足时拒绝整批回滚，不提供强制覆盖或部分恢复。

## 5. 恢复规则

回滚必须在单个`transaction.atomic()`中完成：

1. 已有学生按快照恢复Student字段和原来源批次；
2. 导入前不存在的申请或汇总记录，删除本批创建记录；导入前存在的按快照恢复；
3. 删除本批次思想汇报，再按快照重建原有效明细；
4. 不长期堆积多份inactive历史，不调整现有唯一约束；
5. 本批新建学生只有在来源、关联数据和后续变化检查全部安全时才删除；
6. 任一对象无法安全恢复时整批事务撤销，批次保持`success`。

全部恢复成功后将批次改为`rolled_back`，设置回滚时间和管理员，并记录`rollback_import`审计事件。原始文件、预览、JSON快照、SQLite备份、错误、警告、批次和审计记录继续保留。

## 6. SQLite灾难恢复

`pre_import.sqlite3`仅通过受控管理命令或运维流程恢复：必须维护停机、恢复前再次备份当前数据库、校验来源与完整性，并在恢复后运行迁移、系统检查和数据一致性验证。禁止Web View在线替换数据库文件。

## 7. 测试门禁

至少覆盖权限、方法、最新成功批次、重复回滚、快照缺失或损坏、schema错误、已有学生恢复、新建学生安全删除、材料恢复、唯一约束冲突、事务失败整批撤销、批次字段、审计及灾难恢复安全检查。

## 8. 第一版非目标

- 任意历史批次或部分学生回滚；
- 强制覆盖冲突；
- 数据库快照模型和迁移；
- 全量业务版本化；
- 网页在线恢复SQLite；
- 修改思想汇报唯一约束。

任何路径、状态、快照schema、恢复范围或冲突规则变化，必须同步更新本契约、Module Notes和集成测试并重新Review。
