# 项目CI代码开发与业务逻辑说明

## 1. CI在本项目中的作用

本项目保存学生党务材料，核心风险不是页面样式，而是身份串用、权限越权、Excel误导入、部分写入、
回滚破坏和备份不可恢复。CI把这些业务约束转化为每次合并都必须重复执行的自动门禁。

CI分为两层：

```text
代码层CI
  → 仓库策略
  → Windows/Ubuntu Django全量测试

部署层CI
  → 容器合同
  → Web镜像构建
  → 漏洞扫描
  → Compose HTTPS冒烟
```

代码层回答“业务逻辑是否正确”，部署层回答“同一份代码能否以生产结构安全启动”。两者必须同时
通过，不能用容器启动成功替代业务测试，也不能用单元测试通过替代真实镜像验证。

## 2. 代码层CI开发

### 2.1 入口与触发

`.github/workflows/ci.yml`监听目标为`develop`或`main`的PR，以及这两个分支的push，并支持手工
触发。并发组会取消同一PR的旧运行，避免旧提交结果覆盖新提交。

### 2.2 Repository policy

`scripts/ci_guard.py`实现仓库治理：

- 必须保留业务Spec、设置、依赖、迁移清理和稳定测试文件；
- 禁止跟踪`.env`、SQLite、Excel、上传文件、备份、虚拟环境和Python缓存；
- 禁止把开发者绝对路径写入正式文件；
- 测试后检查仓库根数据库、Excel、上传和备份污染；
- 只豁免冻结的`artifacts/acceptance/`脱敏验收证据目录；
- 检查CI临时SQLite及WAL/SHM边车文件已清理。

这一步保护的是数据治理边界：真实学生数据和运维秘密不能因为测试或导入调试进入Git历史。

### 2.3 双平台Django测试

CI使用Python 3.12，在Windows和Ubuntu分别安装锁定依赖，并将SQLite放入Runner临时目录。执行：

1. `manage.py check`；
2. `makemigrations --check --dry-run`；
3. 空库迁移；
4. Django全量测试；
5. 测试污染检查；
6. 始终清理临时数据库并验证清理结果。

Windows覆盖团队主要开发环境，Ubuntu覆盖正式Docker宿主机方向。双平台同时通过可以发现路径、
编码、文件锁和临时目录差异。

## 3. 部署层CI开发

`.github/workflows/container-ci.yml`和`scripts/container_smoke_test.py`实现DEP-08。工作流使用只读
仓库权限，所有外部Action固定完整提交SHA。

容器CI首先运行静态合同测试，再构建以Git SHA命名的Web镜像。镜像不推送仓库，因此不会产生
未经评审的可部署制品。Trivy只阻断有修复版本的CRITICAL漏洞；HIGH漏洞仍需在评审中登记和处理。

冒烟执行器在`RUNNER_TEMP`创建四个持久化目录和短期TLS证书，显式执行迁移与九支部初始化，
再启动生产Compose。它不会使用`runserver`，而是真实启动Gunicorn单worker和Nginx HTTPS入口。

## 4. CI与业务模块的映射

### 4.1 学生认证和Session

学生使用姓名加学号登录，成功后Session只保存`student_id`。测试验证错误身份不能登录、失败限制
生效、退出只接受安全请求方法，学生不能通过URL参数读取他人档案。管理员和学生Session相互隔离。

对应风险：冒用身份、会话固定、学生横向越权、管理员身份串到学生端。

### 4.2 管理员权限和查询

`viewer_admin`只允许查看，`data_admin`才允许上传、确认、下载原始Excel和回滚。权限必须由后端
装饰器执行，模板隐藏按钮不算权限控制。查询测试覆盖支部、阶段、状态、关键词、分页和非法参数。

对应风险：只读管理员修改数据、未登录访问、未知角色绕过、筛选统计错误。

### 4.3 Excel解析

解析器按第二行表头动态映射列，逐工作表处理九支部，动态识别“第X次思想汇报”。它区分错误与
警告，不猜测列错位或无年份日期，也不把系统计算数覆盖Excel原始总篇数。

对应风险：固定列号导致错读、错误支部映射、日期猜测、思想汇报次数丢失。

### 4.4 上传预览和正式导入

上传后先保存原文件、哈希和服务端`preview.json`，预览阶段不得写学生业务表。确认时重新校验
文件与快照哈希，在`transaction.atomic()`中整批写入；空预览、重复确认和状态冲突返回409。

对应风险：客户端篡改预览、预览即污染业务数据、导入一半失败、重复点击重复写入。

### 4.5 回滚和灾难恢复

业务回滚只允许最近一次成功批次，通过JSON快照恢复已有学生并安全处理本批新建学生。SQLite灾难
恢复必须停机、先校验、恢复前再次备份，不提供网页在线替换数据库入口。

对应风险：回滚非最新批次覆盖后续变化、部分回滚、活动SQLite被替换、恢复源损坏。

### 4.6 备份、监控和容器

生产备份使用SQLite Backup API、一致性校验、SHA-256和COS对象版本。存活端点只验证进程，就绪
端点额外验证SQLite查询。容器CI验证Nginx是唯一公网入口、Web端口不映射、静态资源本地化、
Web重启后数据库仍存在。

对应风险：容器重建丢数据、CDN不可用、Django直接暴露、服务进程存活但数据库不可用。

## 5. 一次PR的完整判定链

```text
提交代码
→ Repository policy检查敏感文件和结构
→ Windows/Ubuntu执行迁移与全量业务测试
→ Container policy验证生产合同
→ 构建当前SHA镜像
→ Trivy检查CRITICAL漏洞
→ 临时HTTPS Compose启动
→ 健康、静态、端口、支部和持久化复查
→ 所有门禁通过后才允许合并
```

失败结果必须修复后重新运行。不得通过删除测试、放宽权限、关闭TLS校验、使用`latest`镜像或把真实
凭据写进CI来换取绿色状态。

## 6. CI不能替代的工作

CI不拥有真实域名、正式证书、云安全组、COS生产凭据或学生数据，因此不能证明系统已经上线。
DEP-09仍需验证第二名成员能按Runbook从零部署；DEP-10仍需在受控Ubuntu主机执行脱敏发布、宿主机
重启、应用回退、COS指定版本恢复和RPO/RTO计时。只有这些人工与自动证据共同通过，才可进入正式
发布审批。
